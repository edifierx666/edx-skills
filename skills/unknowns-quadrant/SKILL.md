# Unknowns Quadrant (未知四象限)

## 核心理念

**地图不是疆域。**

- **地图**：用户对任务的描述（prompt、需求、理解）
- **疆域**：真实的代码库、约束条件、技术实现、业务规则

二者之间的差距就是「未知」。未知越多，Agent 基于猜测做决策的风险越大。Fable 5 的能力上限，取决于你能发现多少自己还不知道的东西。

## 任务目标

当用户表达「我对这块不熟」「不知道从哪下手」「还有什么我没想到的」时，你的任务是：

1. **绘制四象限未知地图**：将用户相对于当前任务的未知，按照「是否意识到」和「是否掌握」两个维度分类。
2. **证据驱动**：每个盲区必须基于真实代码库、文档、技术栈、业务场景的调查结果，不能空想。
3. **只呈现地图**：输出是一份结构化的未知清单，不给建议、不写 prompt、不推荐下一步怎么做——用户会自行权衡取舍。

## 工作流程

### 第一步：理解任务上下文与复杂度评估

从用户的请求中提取：

- **任务目标**：用户想做什么？
- **任务复杂度**：涉及多少模块？需要多少技术栈知识？有多少业务约束？
- **当前阶段**：是任务开始前、进行中、还是遇到问题后的复盘？

**默认假设用户不熟悉**：即使用户提出了明确需求，也要假设他们对实现路径、技术细节、业务约束不完全了解。

**复杂度判断标准**：

- **简单任务**：单一模块、明确技术栈、无复杂依赖（如「修改一个按钮文案」）→ 直接开始调查
- **中等复杂**：涉及 2-3 个模块、常见技术栈、少量业务约束（如「添加一个表单字段」）→ 先简要询问 1-2 个关键问题
- **高度复杂**：跨多个模块、不熟悉的技术栈、复杂业务逻辑（如「重构认证系统」「设计分布式锁」）→ **必须先询问用户** 3-5 个典型问题后再继续

**典型询问问题示例**（根据任务选择）：

```
# 功能类
- 你期望的用户交互流程是什么？(一句话描述)
- 有没有类似功能可以参考？(本项目或其他项目)
- 需要支持哪些边界情况？(空数据、错误、并发等)

# 技术类
- 你对 [技术栈/框架] 的了解程度？(完全不熟 / 用过一点 / 比较熟悉)
- 有没有技术选型偏好？(如前端分页 vs 后端分页)
- 性能/兼容性有特殊要求吗？

# 业务类
- 这个功能涉及哪些角色/权限？
- 有没有业务规则或合规要求？(如审批流、数据脱敏)
- 上下游系统有哪些？
```

**关键原则**：
- 对于高度复杂任务，**不要直接开始调查代码库**，先通过问题确认用户的理解和期望
- 询问问题时，优先问「答案会改变架构设计」的问题
- 每次只问 3-5 个问题，不要一次性抛出 10+ 个问题

### 第二步：调查疆域 (必做)

**不能凭空推测。** 必须通过以下方式真实调查：

1. **代码库调查**
   - 搜索相关模块、组件、API、工具函数
   - 查看现有实现模式、命名约定、架构风格
   - 识别依赖库版本、配置文件、构建工具链
   - 查找类似功能的历史实现、注释、TODO/FIXME
   - **Git 历史回溯**：最近 3-6 个月的相关变更、谁改过、为什么改
   - **Git Blame**：核心逻辑的原始作者和注释，了解决策背景

2. **文档与契约调查**
   - README、架构文档、API 文档、Wiki
   - TypeScript 类型定义、接口契约、GraphQL/Proto/OpenAPI schema
   - 测试用例、Mock 数据、集成测试
   - 错误处理规范、日志规范、监控告警配置
   - **CI/CD 配置**：构建步骤、测试命令、部署策略

3. **技术栈与生态调查**
   - 框架版本特性、已知漏洞、废弃警告
   - 依赖库版本兼容性、peer dependency 冲突
   - 行业通用规范(无障碍、安全、性能、SEO)
   - **浏览器/平台兼容性矩阵**：需要支持的最低版本
   - **环境变量与配置**：不同环境(开发/测试/生产)的差异

4. **业务场景调查**
   - 边界条件(空数据、极大值、并发、弱网)
   - 用户角色与权限、RBAC 模型
   - 跨平台需求(移动端、不同浏览器、SSR/CSR)
   - 上下游系统依赖、消息队列、定时任务
   - **国际化(i18n)**：是否需要多语言、日期/货币格式
   - **数据持久化**：缓存策略、降级方案、数据迁移

5. **运行时与可观测性调查**
   - 错误上报系统(Sentry 等)
   - 日志级别与格式
   - 性能监控(PERF metrics、Core Web Vitals)
   - 灰度发布、Feature Flag 管理
   - 容量规划与限流策略

### 第三步：按象限分类未知

基于调查结果，将未知分配到四个象限。每个象限内按**认知距离**分组：

**认知距离**指的是这个盲区与用户当前认知的差距：
- **与假设冲突**：用户以为是 A，实际是 B（最需要关注）
- **未考虑过**：用户根本没想到这个方面
- **可以利用**：用户不知道但可以直接用的资源

不同象限的分组策略：

- **I. 已知的已知**：不分组，直接列出需求点
- **II. 已知的未知**：按阻塞程度分组（核心疑问 / 待确认细节 / 可选探索）
- **III. 未知的已知**：按认知距离分组（与假设冲突 / 可直接利用 / 团队约定）
- **IV. 未知的未知**：按认知距离分组（与假设冲突 / 未考虑场景 / 隐藏风险）

## I. 已知的已知 (Known Knowns)

用户已在需求中明确表达的部分。**默认假设用户不熟悉技术细节**，因此这一象限不是简单确认需求，而是把每个需求点背后的功能、逻辑、涉及内容详细展开解释，让完全没接触过代码的用户也能看懂。

### 需求点详解

针对用户提出的每个需求点，详细解释：

#### [需求点 1：名称]
- **用户表达**：[原始需求描述]
- **这是什么**：[用大白话解释这个需求本质上在做什么，假设用户零基础]
- **技术含义**：[该需求在代码层面实际意味着什么，涉及哪些技术环节]
- **涉及模块**：[会触及哪些代码模块、文件、依赖，每个模块负责什么]
- **工作原理**：[数据/流程如何流转，用户操作后会发生什么]
- **需确认**：[如果内容复杂，列出需要向用户确认的关键决策点]

#### [需求点 2：名称]
- **用户表达**：...
- **这是什么**：...
- **技术含义**：...
- **涉及模块**：...
- **工作原理**：...
- **需确认**：...

### 明确约束条件

对每个约束也要解释清楚它意味着什么：

- **性能要求**：[用户是否明确？如「首屏加载 < 2s」意味着需要代码分割、懒加载等]
- **兼容性要求**：[浏览器版本、移动端、IE 等，各自意味着什么限制]
- **安全合规**：[GDPR、等保、行业规范，具体约束是什么]
- **交付时间**：[是否有硬性截止日期]
- **资源限制**：[人力、预算、第三方服务配额]

> **输出原则**：默认用户完全没接触过代码。即使他们说「要做一个用户列表」，也要展开解释「接口调用是从服务器拿数据、分页是把大量数据分批展示、权限控制决定谁能看到什么、空态处理是没数据时显示什么、加载状态是等待时的转圈提示」等，让用户真正理解每个部分在做什么。

## 关键原则

### 1. 证据驱动，拒绝臆测

每个盲区必须基于真实调查结果：

- ✅ **正确**：「`src/utils/request.ts` 中已有全局错误拦截器，会自动重试 5xx 错误」
- ❌ **错误**：「一般来说，项目应该会有错误处理机制」

如果某个领域无法调查(如用户权限不足、文档缺失)，明确标注「未能确认」。

### 2. 按认知距离分组

盲区按「认知距离」分组，而不是按「严重程度」分级：

- **II. 已知的未知**：按阻塞程度分组（核心疑问 / 待确认细节 / 可选探索）
- **III. 未知的已知**：按认知距离分组（与假设冲突 / 可直接利用 / 团队约定）
- **IV. 未知的未知**：按认知距离分组（与假设冲突 / 未考虑场景 / 隐藏风险）

这样分组符合用户的认知心理：人对「与假设冲突」的信息最敏感。目标是帮助用户补全认知，而不是列出要修的 bug。

### 3. 区分「未知」与「未决策」

- **未知**：客观存在但用户不知道的事实(如历史 bug、依赖废弃、现有组件)
- **未决策**：需要用户主观判断的选择(如 UI 交互细节、性能目标、功能优先级)

「未决策」属于 **II. 已知的未知**，需要标注「待用户确认」。

### 4. 只呈现地图，不给路线

输出是一份结构化的未知清单，**不包括**：

- ❌ 「建议你在 prompt 中补充 XXX」
- ❌ 「下一步应该先解决 YYY」
- ❌ 「你的 prompt 缺少 ZZZ」
- ❌ 「我推荐使用 AAA 库」

只在 **III. 未知的已知** 中，可以用「建议」字段说明如何利用已有资源(因为这是陈述事实)。

用户拿到地图后，会自行权衡：哪些盲区值得在 prompt 中明确，哪些交给 Agent 灵活处理，哪些暂时忽略。

### 5. 领域不熟时先做盲区扫描

如果用户表达「我对这个领域一无所知」(如「不知道什么是调色」「没用过这个框架」)，优先进行**领域盲区扫描**：

- 搜索权威文档、官方教程、最佳实践
- 列出核心概念、术语、工作流程
- 标注常见陷阱、历史问题、废弃特性
- 在 **IV. 未知的未知** 中补充领域知识缺口

## 示例场景

### 场景 1：接口字段不确定

**用户**：「我要做一个用户列表页，但不确定接口返回哪些字段。」

**调查**：
- 搜索 `api/user` `getUserList` `IUserResponse`
- 检查类型定义、Mock 数据、Swagger 文档
- 查看现有用户相关页面如何消费数据
- 检查权限中间件，是否有字段级权限控制

**输出象限分布**：

**I. 已知的已知**：

#### 需求点：展示用户列表
- **用户表达**：做一个用户列表页
- **这是什么**：在网页上显示一个表格，每一行代表一个用户，包含用户名、邮箱、角色等基本信息
- **技术含义**：需要「接口调用 → 数据解析 → 表格组件渲染 → 分页加载 → 空态/错误处理」
- **涉及模块**：
  - `src/pages/UserList.tsx`：页面入口，负责把筛选条件和子组件串起来
  - `src/api/user.ts`：封装了用户相关的接口调用
  - `src/components/Table`：通用的表格组件，负责渲染和交互

- **这是什么**：认证提供商是第三方登录服务，让用户不用记住你网站的密码，直接用 Google/GitHub 账号登录你的网站。本质上是"借用"大厂的账号体系
- **技术含义**：需要「OAuth2 授权码流程 + 跳转回调处理 + Access Token 存储 + 用户信息映射 + 会话管理」

  3. 你的后端用 code 向 Google 换取 access token
  4. 用 access token 向 Google 请求用户信息(邮箱、头像等)
  5. 在你的数据库中创建或关联用户记录
  6. 生成你自己的 session/JWT，让用户保持登录状态

## 常见遗漏盲区清单

以下是跨项目高频出现但容易被忽视的盲区类型，调查时优先检查：

### 数据层盲区

- **数据迁移**：新字段是否需要回填历史数据？迁移脚本是否幂等？
- **数据一致性**：分布式场景下的最终一致性延迟、缓存失效策略
- **数据删除**：软删除 vs 硬删除、级联删除规则、GDPR 删除权
- **数据脱敏**：日志中是否泄露敏感信息？前端是否接收到不该看的字段？
- **数据备份**：是否有定期备份？恢复演练是否做过？

### 并发与竞态盲区

- **乐观锁**：表单提交时是否检查版本号？并发编辑冲突如何解决？
- **幂等性**：重复提交、网络重试、消息队列重复消费如何保证幂等？
- **分布式锁**：多实例场景下的资源竞争、锁超时、死锁检测
- **前端竞态**：快速切换 Tab 时旧请求覆盖新数据、Promise.race 陷阱
- **定时任务冲突**：Cron 任务是否会并发执行？是否需要分布式调度？

### 边界条件盲区

- **空数据**：列表为空、详情不存在、接口返回 null 时的 UI 展示
- **极值数据**：长文本溢出、大数精度丢失、超大文件上传、深层嵌套对象
- **特殊字符**：SQL 注入、XSS、CSV 注入、文件名非法字符
- **网络异常**：超时、断网、弱网、接口降级、CDN 挂掉
- **时区与时间**：夏令时、闰秒、不同时区展示、倒计时跨天

### 权限与安全盲区

- **IDOR 漏洞**：通过 ID 遍历访问他人数据
- **越权操作**：前端隐藏按钮 ≠ 后端鉴权、URL 直接访问绕过权限
- **Token 泄露**：localStorage 被 XSS 读取、日志中打印 token
- **CORS 配置**：生产环境是否配置了通配符 `*`？预检请求是否正确？
- **Rate Limiting**：是否有防刷限制？验证码是否必要？

### 可观测性盲区

- **错误上报**：哪些错误会上报？上报率是否过高导致淹没真实问题？
- **日志脱敏**：用户手机号、邮箱、密码是否误入日志？
- **性能监控**：首屏加载、接口耗时、内存泄漏、卡顿检测
- **告警配置**：核心接口失败率、依赖服务异常是否有告警？
- **灰度可观测**：Feature Flag 开关状态、灰度用户标识

### 国际化与本地化盲区

- **多语言**：是否需要支持？翻译来源？动态切换还是编译时？
- **日期格式**：MM/DD/YYYY vs DD/MM/YYYY、12/24 小时制
- **货币与数字**：千分位分隔符、小数点、货币符号位置
- **字符集**：emoji 是否正确存储？CJK 字符计数问题
- **RTL 语言**：阿拉伯语、希伯来语的布局镜像

### 移动端与跨平台盲区

- **Safe Area**：刘海屏、底部导航栏遮挡
- **触摸事件**：300ms 延迟、滚动穿透、双击缩放
- **键盘行为**：输入框被遮挡、键盘收起时机、虚拟键盘高度
- **WebView 差异**：iOS WKWebView vs Android WebView、第三方浏览器内核
- **APP 内嵌 H5**：JSBridge 调用、权限授权、返回键劫持

### 依赖与版本盲区

- **Breaking Changes**：依赖库大版本升级的不兼容改动
- **安全漏洞**：npm audit、Snyk 扫描出的高危漏洞
- **废弃警告**：deprecated API 是否有替代方案？何时移除？
- **Peer Dependency**：版本冲突、多个实例共存问题
- **Monorepo 影响**：子包变更是否影响其他包？版本发布顺序？

### 测试与 CI/CD 盲区

- **测试覆盖率**：核心逻辑是否有单测？边界条件是否覆盖？
- **E2E 稳定性**：Flaky 测试、等待时机、环境依赖
- **构建缓存**：缓存失效导致的增量构建错误
- **部署回滚**：回滚方案是否验证过？数据库 schema 是否兼容回滚？
- **环境一致性**：开发环境 vs 生产环境的配置差异、数据差异

### 业务逻辑盲区

- **状态机完整性**：所有状态转换路径是否覆盖？逆向流程是否支持？
- **工作流中断**：用户中途退出、浏览器崩溃、长时间无操作时如何恢复？
- **库存超卖**：高并发下的扣减逻辑、补偿机制
- **优惠叠加**：多种优惠券、折扣、积分的计算优先级
- **审批流转**：审批人离职、审批超时、驳回后重新提交

## 反模式 (禁止)

### ❌ 对"已知的已知"一笔带过

```markdown
## I. 已知的已知

- 需要做一个用户列表
- 支持分页
```

**问题**：没有展开技术含义，没有详细解释涉及内容，用户可能对"用户列表"和"分页"背后的技术环节完全不了解。

**正确做法**：

```markdown
## I. 已知的已知

#### 需求点：用户列表展示
- **用户表达**：需要做一个用户列表
- **这是什么**：在网页上显示一个表格，每一行代表一个用户，包含用户名、邮箱、角色等基本信息
- **技术含义**：需要「GET 接口调用(从服务器拿数据) + 表格组件(把数据变成可视化的行列) + 数据映射(把后端字段对应到表格列) + 加载状态(等待时显示转圈) + 空态处理(没数据时显示提示) + 错误处理(接口失败时显示错误信息)」
- **涉及模块**：
  - src/pages/UserList.tsx：页面入口，协调各个组件
  - src/api/user.ts：封装接口调用，统一错误处理
  - src/components/Table：通用表格组件
- **工作原理**：用户打开页面 → 调用 GET /api/users → 接口返回数据 → 表格逐行渲染
- **需确认**：是否需要实时刷新？是否需要导出功能？

#### 需求点：分页支持
- **用户表达**：支持分页
- **这是什么**：用户数据太多时，不是一次性全部展示，而是分成多页，每页显示固定数量（如 20 条）
- **技术含义**：前端分页(全量数据客户端切片) vs 后端分页(传 page/size 参数，服务端只返回一页) — 影响性能和实现复杂度
- **涉及模块**：分页组件、接口参数、URL query 同步
- **工作原理**：用户点击第 2 页 → 发送 ?page=2&size=20 → 后端返回第 2 页数据 → 表格刷新
- **需确认**：数据量预期多大？是否需要 URL 记录分页状态以便分享链接？
```

### ❌ 空想未知

```markdown
## IV. 未知的未知

#### 性能问题
- **发现**：大数据量可能导致性能问题
- **证据**：一般来说，列表数据多了会卡
```

**问题**：没有真实调查，只是泛泛而谈。

**正确做法**：搜索现有列表组件，检查是否有虚拟滚动、分页加载；查看 issue 中是否有性能投诉；查看性能监控数据。

```markdown

- **发现**：现有 `<Table>` 组件未实现虚拟滚动，在 1000+ 行数据时会出现明显卡顿
- **证据**：src/components/Table/index.tsx L45-67 使用普通 map 渲染；GitHub issue #3421 报告了订单列表卡顿问题

- **触发条件**：管理员查看全量用户列表、导出前预览数据
```

## 与其他 Skill 的协作

- **`api-field-contract-guard`**：如果未知涉及接口字段，在 **II. 已知的未知** 中标注，但具体字段确认流程交给该 skill。
- **`understanding-code-logic`**：如果用户对代码流程不熟，先用该 skill 建立心智模型，再做四象限扫描。
- **`reachable-flow-audit`**：如果未知涉及「代码是否真会执行」，在 **IV. 未知的未知** 中标注可达性风险。
- **`gstack-investigate`**：如果未知是「现有 bug 的根因」，标注后建议用户单独启动 debug 流程。

## 何时不适用

以下情况**不应**使用本 skill：

- 用户已经给出详细的技术方案，只是让你实现 → 直接实现，无需扫盲区
- 用户问「怎么做 X」，期待的是教程或代码示例 → 给教程，不是未知地图
- 任务过于简单(如「写一个 Hello World」) → 没有有意义的未知
- 用户明确说「不用分析，直接动手」 → 尊重用户意图

## 输出美学

四象限地图是一份**决策辅助文档**，应该：

- **结构清晰**：四个象限独立成章，1-3 级分级明显
- **扫描便捷**：优先级高的盲区放最前面，用户快速浏览后能决定哪些要处理
- **证据充分**：每个条目都有「位置」「证据」「影响」，不是空口断言
- **视觉友好**：使用 emoji(✅ ❌ ⚠️ 📍) 和表格辅助阅读，但不过度装饰

最终目标：用户看完地图，能够**自信地**给 Agent 补充上下文，或者**自信地**决定哪些未知可以交给 Agent 灵活处理。
