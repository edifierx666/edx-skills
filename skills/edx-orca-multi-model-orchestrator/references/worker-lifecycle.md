# 统一 worker 生命周期与证据契约

总指挥将本文件全文放入 XML spec 的 `<lifecycle_contract>`（需求审计官另在 `<audit_spec>` 附原文审计规范），结构见 coordinator-protocol「Worker spec XML 结构」；worker 不依赖相对路径可读性。

- 只用当前 Orca preamble 的可执行文件、handle、Task ID、Dispatch ID。自然检查点及完成前检查追加指示。`check` 返回 `consumer_fenced` 立即停止，不重试 check、不发送完成事件；send/ask 的同名错误先停止副作用并按 worker-contract 核实调用终端身份，禁止沿用过期身份。
- `worker_done` 是一次逻辑完成事件；完成报告发送后停止 check、轮询和新工作。响应丢失不盲目重复发送：由 coordinator 先 request-show，再核对 Task/Dispatch；只有当前 recovery guide 允许时才用相同 request ID、相同命令精确恢复。没有 request 身份或结果不唯一就停止并升级，不能新建完成事件猜测补发。
- 工具调用失败不等于 Orca Task/Dispatch 终态，也不自动证明 child 完成或失败。父 worker 必须把失败记录为内部执行事件，区分调用未启动、命令已执行但非零、错误后有可核验后续结果和错误后没有最终结果；继续执行不等于重试失败调用。
- 每个工具错误事件至少记录工具/命令、cwd、时间、错误或 exit code、是否可能产生副作用、是否重试、恢复结果和未执行项。只有确认没有副作用且工具契约允许时才能有限重试；结果可能已产生副作用但状态不确定时先对账或停止依赖该结果，禁止盲目重试、静默换模型/Agent 或并行重复执行。
- 父 worker 必须逐项登记每个必需和可选 child 的状态、结果、错误与证据。内部 child 的本地状态使用 `not_started | running | completed | failed | blocked | unknown`，不把它冒充成 Orca API 枚举；`completed` 只表示有可核验最终结果，不表示发现或质量门通过。
- 必需 child 未完成、失败、阻塞、状态未知、报告缺失或证据不足时，父 worker 不得用 `worker_done --outcome succeeded` 表示整体任务已完成；无法恢复时用 `failed` 或 escalation 报告已完成部分、遗留项和所需动作。部分结果不得包装为整体 PASS、SHIP 或完成。
- `--outcome succeeded` 仅表示角色任务完成并提交可读报告，不等于质量 PASS。测试员测试执行完成但产品测试失败，可以 succeeded，但 verification_status 必须 failed；审查员只有 SHIP 才过审。没有完成任务用 failed。execution_status、verification_status、review_verdict、fact_status 由 coordinator 账本分开记录，不是虚构的 Orca API 字段。
- 报告包含 Run/Task/Dispatch、stage/revision、spec 和输入/输出 hash、实际命令、cwd、时间、exit code、关键输出/证据路径、未执行项与原因；effective model 以 coordinator 的 launch.effective 回执为准。摘要不替代真实执行证据，凭证与敏感值必须脱敏。
- `--report-path` 必须指向实际存在的报告文件，不能填目录。只读角色只可写 spec 明确独占的 report-file Ownership；artifact/render/测试输出目录另列并授权。未经授权不运行会写入其他路径的检查，不清理别人改动以伪造干净状态。
- 参与 reviewer、fact-checker、editor 或 red-team 时，spec 必须提供该输入范围的 authorFamilies（所有实际内容作者已核实 effective family 的并集，含测试、编辑、修复及整合作者）。前三者排除整个 authorFamilies，红方另排除相关 reviewer family 集合；集合缺失、家族未知或自身命中禁用集合时先 ask 并停止该阶段，不能自动拆审冒充整体终审。
- 所有模式包括 worktree 均默认不 commit、不执行 git 写操作、不越界。worktree 与提示词不是权限沙箱；数据/provider policy 未确认、权限控制未核实或出现基线重叠时停止并 ask。不得自行更改权限设置。修复后旧验收证据失效，等待新 revision。

## Worker 自主决策与交付声明

`worker_done` 的角色专属 body 和报告除角色要求外，按任务复杂度简短覆盖以下声明；无事项也要明确写“无”，不得用省略代表没有：

- **动作与决策偏离**：记录关键动作、尝试路径和产物；将自主选择分别归为“指令空白”“遇阻折中”“范围微调”，每项按“原因 → 决定 → 影响与回退方式/位置”说明。没有偏离时写“无自主偏离，按 spec 执行”。
- **自主权边界**：仅当选择处于已授权 Ownership/权限内、可逆且不改变核心目标时，可先推进再披露。遇到核心目标冲突、关键前提缺失而只能猜测、不可逆/破坏性动作、外部发布，或权限、隐私、数据策略不明时，暂停相关动作并 ask/escalate；不得以事后披露替代授权。
- **完整性与现场**：列明产物范围/数量、未完成或未覆盖项；披露 TODO/占位、截断、省略、mock/hardcode，以及跳过或弱化的测试/校验，并说明是否由 spec 授权。列出本次创建的临时文件、依赖、配置变更和后台进程及其清理状态；只清理归属明确且获准处理的自身产物，不删除用户/他人文件或未知归属资源，无法清理则报告位置和原因。Mock 可用于已授权的测试/fixture，但不得静默替代要求的真实路径。
- **逻辑缺口**：不能只报跑通的主流程（Happy Path）。主动列出三类缺口：[异常与逆向流缺失] 未处理的失败回滚、超时/重试、空状态与极端值、重复操作/并发、取消与退款等逆向流程；[原需求逻辑漏洞] 执行中发现的需求自相矛盾、未闭环或考虑不周之处，不得装作没看见硬写；[上下游连锁断层] 本次改动在当前范围跑通，但会让范围外的关联模块、章节、历史数据或下游环节失效或断链。已全面闭环时写“主逆向逻辑已闭环”。缺口只报告不擅自扩大范围去补；需求矛盾导致无法继续时按自主权边界暂停并 ask。
- **约束与信源**：简述 spec 中关键限制，尤其禁止修改项及遵守情况；区分本次工具实际读取/检索所得、用户/spec 提供和模型先验推断。工具未取到或无法核实的信息标为未核实/先验，不得写成实时查证。

报告只陈述可观察事实；“无”声明不代替检查。worker 自报不构成 Orca 状态、清理成功或质量门通过的独立证明。

## Coordinator 用户可见汇报契约

这是 coordinator 写给用户的本地报告格式，不是 Orca API 状态；适用于 `complete`、`partial`、`incomplete`、`unknown`、`escalation` 全部结论。目标是让用户 5 秒看懂每个 worker 干了什么、交了什么、自己拍了什么板、还漏了哪些逻辑、哪里要用户决定。篇幅随复杂度伸缩：顺利的部分一两句带过，有曲折、偏离或风险的部分展开；没有内容的项整项省略，不写“无”“无自主偏离”“无需拍板”之类的占位。

**写给用户的是任务事实，不是编排运维。** Run/Task/Dispatch/Delivery/message ID、心跳、ack、回执、worker 终端与资源结算、`launch.effective`、hash 等 Orca 记账细节留在 manifest/ledger，正文最多一句“编排记录见 manifest 路径”。只有它们直接影响结论时（worker 失败/失联/状态无法对账、资源无法释放、模型或额度与计划不符）才写进正文，并用用户能懂的话说明影响。流程图只画任务本身的数据/工作流，不画 Orca 调度。

按以下四部分输出：

1. **调度全景**：一两句写清派了哪几个 worker、各自职责、串行还是并行、整体结果与把握度（高 / 中 / 存在推测）。
2. **逐 worker 施工明细**：每个 worker 单列，不得合并摘要吞掉过程：
   - **干了什么**：用 `动作 A ➔ 动作 B ➔ 动作 C` 写真实做过的关键步骤，包括试错与转向；提炼实质动作，不贴原始日志。
   - **交出了什么**：新增/修改的具体对象（文件、数据、章节），加用户能直接抽查的凭证：开发类写命令与结果摘要（如 `12 passed, 0 failed`）或改动位置；调研/数据类写出处链接、关键摘录或数量闭合；内容类写约束对齐情况。未验证的写“【未验证】+原因”。
   - **⚡ 自作主张与偏离**：只在有偏离时写，按 [空白脑补] / [遇阻折中] / [范围微调] 分类，每条一句 `[原因] ➔ [擅自做的决定] ➔ [怎么改回来/推翻成本]`。
   - **🕳️ 逻辑缺口与未覆盖盲区**：只在有缺口时写，按 [异常与逆向流缺失] / [原需求逻辑漏洞] / [上下游连锁断层] 分类，每条写清缺了什么、不补会造成什么后果（如“取消订单时积分不会退回”）。主流程跑通但逆向流程、边界或下游未处理时，worker 状态写成“主流程已完成，存在 N 处逻辑缺口”，不得只写“已完成”。
3. **防坑自检**：逐项核对 ①缩水/占位/Mock/被注释的校验 ②是否只验证了主流程，报错处理、边界极值和逆向流程留白（有留白必须已写进对应 worker 的逻辑缺口）③临时文件、依赖、配置等现场残留 ④用户禁止项/保持不变项是否守住 ⑤事实是否来自本次工具实查，靠模型先验的标 `[基于模型先验知识]` ⑥多个 worker 的假设、字段、格式、风格是否冲突。全部干净时合并成一行 `✅ 防坑自检：全清`；触发任何一项都用 ⚠️ 单列，写清是哪个 worker、在哪、怎么处理。
4. **待你拍板与补漏建议**：把需要用户确认的自主决定、需求逻辑漏洞、未覆盖的逻辑缺口、未验证项和风险汇成编号短清单，写成选择题或下一步补漏建议，用户可以逐条批准、明确规则或指派某个 worker 补齐；没有则省略本部分。

`complete` 仅在所有必需 child 有可核验最终结果、关联 Orca 状态已对账且证据齐全时成立；不完整结论首行写“未形成可信的整体完成结论”，并在调度全景说明哪些 worker 没完成、为什么、下一步。`worker_done`、工具错误和 projection 不能替代 Orca 状态或原始凭证；这些核对由 coordinator 在 ledger 完成，正文只写结论。
