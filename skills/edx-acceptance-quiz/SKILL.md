# 验收考试（Acceptance Quiz）

## 核心边界

这是一次只读的理解验收：读取代码和历史，生成报告与测验，但不修改源代码、测试、配置或依赖。发现代码问题时记录证据，不顺手修复。

验收分为两道独立门槛：

1. **理解门槛**：用户能否解释改动的动机、行为和风险。
2. **工程门槛**：测试、运行验证和未解决风险是否达到项目的合并要求。

答对测验只证明理解门槛通过；只有工程门槛也有充分证据时，才建议合并。

## 流程

### 1. 锁定验收范围

按优先级确定唯一范围：用户指定的 PR / commit / 文件列表，其次才是当前 `git diff` 或最近 commit。记录：

- 基线与目标 commit SHA；
- 工作区是否存在未提交修改；
- 纳入验收的 changed files；
- 排除的混合改动及理由。

如果当前不是 Git 仓库，先说明无法提供版本绑定的验收结论；如果改动彼此混杂或范围仍有歧义，先报告当前可观测范围：工作区状态、最近 commit、相关文件和未提交差异，并将内容分为“已确认纳入”“疑似相关但未确认”“明确排除”。只有当不同范围会导致结论互相矛盾，或用户要求合并/发布级结论时，才暂停并请用户圈定 PR、commit 或文件；不得把范围不确定自动扩大成整个仓库，也不得因此放弃所有只读分析。

**完成标准：** 每个纳入验收的文件都有明确来源，所有已知混合改动均已纳入或显式排除，报告可绑定到一个可复查的版本快照。

### 2. 收集改动全貌

- 追踪每项改动如何与既有代码交互：谁调用它、它触发什么、哪些行为因此改变。
- 检查 diff 之外的隐性影响：默认值、状态转换、时序、错误路径、边界条件和被删除的旧行为。
- 区分已有验证证据与尚未验证的假设，不把“用户理解”替代为“代码正确”。

**完成标准：** 每项用户可感知或契约级变化都有调用链或代码证据；每项重要风险都标记为已验证、未验证或不适用。

### 3. 生成理解报告

默认在 `.__docs` 生成 HTML 报告；用户明确要求时可使用 Markdown。报告包含：

1. **验收快照**：commit、工作区状态、纳入与排除范围。
2. **动机与上下文**：为什么做、解决什么问题。
3. **设计直觉**：关键决策及放弃的替代方案。
4. **数据流与调用链**：按行为组织，不按文件堆清单。
5. **行为变化**：改动前与改动后的用户可感知差异。
6. **风险与边界**：已处理、未验证和明确搁置的场景。
7. **工程证据**：测试、运行验证及其缺口；未执行的项目必须如实标记。

聊天中给出报告路径和摘要。

**完成标准：** 报告文件已生成且可读取，包含版本快照、全部重要行为变化以及工程证据状态。

### 4. 出理解题

在报告底部出题：

- 大型改动通常 5–8 题；单文件且不改变公开接口、数据结构或异步流程的小修复可降为 2–3 题，必要时直接说明无需考试。
- 题目考行为推演和设计理解，例如“输入 X 会发生什么”“为什么不能直接 Y”。
- 覆盖最重要的决策和最容易忽略的隐性影响。
- 混合选择题与简答题；选择题干扰项来自真实误解。
- 答案放在报告末尾折叠区，或等用户作答后再核对。

**完成标准：** 每个关键决策或高风险隐性影响至少被一道题覆盖，题目本身不泄露答案。

### 5. 核对版本与答案

用户作答前重新检查当前版本快照。若代码、commit 或纳入范围已变化，原报告和测验立即过期，必须基于新快照重新生成。

逐题核对答案：

- 答错时说明误解、正确行为和代码证据，再换角度复测该知识点。
- 全部答对时，将理解门槛标记为通过。
- 复测后仍未理解时，列出尚未掌握的决策点，将理解门槛标记为未通过并结束考试；是否继续合并由用户明确决定，Skill 不替用户判定通过。
- 用户疑问暴露代码问题时，如实加入风险清单。

最后分别报告理解门槛与工程门槛。只有两者都通过，才明确建议合并。

**完成标准：** 每道题都有判定与证据，考试终态只能是“理解通过”或“理解未通过”，工程门槛另有独立结论。
