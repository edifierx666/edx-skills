# SkillCAT 技能自进化

把「同一任务有成有败」的真实执行经历，提炼成**经过回放验证**的规则补丁，用来升级一个已有的 skill / prompt / 规则文件，或从零沉淀一个新 skill。方法来自论文 SkillCAT（arXiv:2606.13317），拒绝两种常见做法：凭单次成功写经验（运气会被误记成技能），以及不验证就往文件里堆规则（论文实测某类未验证补丁会让成功率**下降** 6 个百分点）。

## 输入

缺一则先向用户要，不要凭空开工：

| 输入 | 说明 |
| --- | --- |
| 进化目标 S₀ | 已有的 SKILL.md / prompt / CLAUDE.md 规则段；新建模式则为空 |
| 执行经历 | 同一任务（或同类任务）的多次尝试，**每次带成功/失败标注**。来源优先级：用户贴的会话记录或日志 > 本次会话刚发生的尝试 > 用户同意后主动对同一任务多跑几次 |

只有一条轨迹、或用户只说「感觉不好用」拿不出失败案例时，明确告知：本方法的证据基础是成败对比，没有对比只能做低置信的常规 review，不伪装成有证据的进化。

## 产出

固定三样：

1. **升级后的文件**（或新 skill 目录）——改动融入原有章节结构，不是末尾追加流水账
2. **补丁审计表**——每条候选规则的去留和理由，在对话中展示，被拒的不静默丢弃
3. **落盘前的 diff 要点**——展示改了哪些章节、加删了哪些规则，征得同意再写文件

## 输出位置

| 场景 | 落点 |
| --- | --- |
| 进化已有文件（默认路径） | **原地更新**：源文件在哪就改哪，不改变它的级别 |
| 新建 skill，教训依赖本项目 | `<项目>/.claude/skills/<name>/SKILL.md`（项目级，**默认**） |
| 新建 skill，教训是通用方法论 | 提请用户确认后才写 `~/.claude/skills/`（全局） |
| 审计表留档（仅用户要求时） | `<项目>/.__docs/skill-evolution/<name>-<日期>.md` |

项目级还是全局的判据：规则里出现本项目的目录名、接口、业务名词 → 项目级；纯方法论、换个项目照样成立 → 全局候选。一批补丁两者混合时拆开落盘：项目特有的落项目级，通用的单独列出请用户决定。

## 触发示例

- 「xlsx skill 这周失败三次成功两次，把教训合进去」→ 进化模式，原地更新那个 skill 文件
- 「这个项目里我老忘记先跑 codegen，把这条沉淀成 skill」→ 新建模式，写入项目 `.claude/skills/`

## 审计表长这样

```markdown
| # | 候选补丁（一句话） | 来源任务 | 分水岭 | 回放判定 | 分数 | 去留 |
|---|---|---|---|---|---|---|
| 1 | 改 xlsx 前先只读打开确认 sheet 名 | 任务A: 合并报表 | 第3步:失败侧按猜测的sheet名直接写入 | 失败→成功 | 3 | ✅ 合入 |
| 2 | 输出前校验公式单元格是否为 #REF! | 任务A: 合并报表 | 第7步 | 成功→成功(无回归) | 2 | ✅ 合入 |
| 3 | 遇到大文件先拆分处理 | 任务B: 数据清洗 | 无对比对(两次全失败) | 失败→失败(推演后仍失败) | 1 | ❌ 没修到根因 |
| 4 | 总是先列出所有文件再操作 | 任务C | 第1步 | 成功→失败(多余步骤引入超时) | 0 | ❌ 引入回归 |
```

## 执行流程

### Step 1 — 找分水岭，写经验记录

对每个任务，把成功轨迹和失败轨迹的**动作序列**对齐，找第一个分岔步。分岔点之前是公共前缀（无信息量），之后是连锁错误（是果不是因），所以每条经验记录只写分岔点：

```markdown
## Record: 合并两个 xlsx 报表（任务A）
- 分水岭: 第 3 步。成功侧先只读打开列出 sheet 名；失败侧直接按猜测的
  "Sheet1" 写入，实际叫 "汇总"，KeyError 后连锁重试 4 次全废
- 失败归因: skill 没有要求「写前确认结构」，模型默认了 sheet 命名假设
- 可编辑教训: 当要写入已存在的 xlsx 时，先只读打开列出全部 sheet 名，
  禁止按猜测的 sheet 名直接写
- 置信度: contrastive
```

轨迹结局分布的三种情况：

| 分布 | 处理 |
| --- | --- |
| 有成有败 | 各取一条组成对比对——核心路径 |
| 全成功 / 全失败 | 降级：单轨迹提取，记录标 `single-trace` 低置信；或跳过 |
| 跨任务凑对 | **禁止**。任务难度差异会被误判成技能差异 |

### Step 2 — 回放验证，打分筛选

每条记录转成一个候选补丁（对 S₀ 的一处增/改），逐个验证。验证方式按可行性降级：

1. **真实重跑**：补丁临时并入 S₀，重跑源任务看结局
2. **推演回放**：沿失败轨迹走到分水岭那一步，检查「当时上下文里若有这条规则，会不会改选正确动作」——必须落到那一步的具体上下文，不接受「应该有帮助」这种泛泛判断
3. 都不可行 → 标 `unverified`，本轮不合入

按结局迁移打分，**门槛 ≥ 2 分才合入**（不放宽）：

| 基线 → 回放 | 分数 | 含义 |
| --- | --- | --- |
| 失败 → 成功 | 3 | 修复了失败，最强证据 |
| 成功 → 成功 | 2 | 保持行为，无回归 |
| 失败 → 失败 | 1 | 没修到根因，拒绝 |
| 成功 → 失败 | 0 | 引入回归，坚决拒绝 |

### Step 3 — 合并落盘

- 先合 2 分补丁，再合 3 分补丁——冲突时高分规则覆盖低分规则
- 每条新规则放进 S₀ 语义最贴近的既有章节；与旧规则语义重复的收敛成一条；直接矛盾的高分侧胜出并删掉旧条目
- 按「输出位置」表确定落点，出审计表和 diff 要点，征得同意后写文件

### Step 4（可选）— 拓扑重组

skill 超过约 150 行、且多数任务只用到其中一部分时，重组为「常驻核心 + 按需节点」：一级标题内容任何任务都加载；二级节各自带一行路由元数据（keywords / summary / deps），使用时按任务挑 top-7 节点拼装，不重写正文。skill 不大时跳过——全量加载更简单。

## 质量标准

- 每条合入的新规则都能回答「哪次失败逼出了它」——指得出具体任务和具体分岔步骤
- 新规则是带触发条件的祈使句（「当 X 时，先做 A，不要做 B」），不是「注意 Y」式的空泛提醒
- 审计表里有被拒绝的补丁——如果所有候选全部通过，说明验证是走过场
- 进化后的 skill 没有变成流水账：规则数量增长克制，语义重复的旧规则被收敛而非并存
