# 盲区扫描（Blindspot Scan）

## 核心理念

地图不是疆域。用户交给你的需求是地图，代码库和现实约束才是疆域，两者的差距就是「未知」。用户最大的风险来自「未知的未知」——不知道该问什么问题、不知道「好」的标准长什么样、不知道有哪些历史工作和坑。

这个 skill 的目标不是替用户完成任务，而是**把用户的未知变成已知，让用户能写出更好的需求**。

同时警惕：扫描者自己也有盲区。你的扫描结果混着「验证过的事实」「通用知识」和「推测」，如果不区分就端给用户，等于用权威的口吻制造新盲区。

## 优先级规则

- 用户想**理解现状怎么工作**（"分析这个模块""这个页面怎么跑的"）→ `understanding-code-logic`
- 用户**准备动手但对领域不熟**、要写需求、怕踩坑（"我对 X 不熟""不知道从哪下手"）→ 本 skill
- 两者兼有时：先由本 skill 产出盲区报告，报告中把"值得深入理解的模块"列为下钻方向，交给 `understanding-code-logic` 承接

## 流程

### 1. 摸清用户的出发点

先用一两个问题确认（一次只问一个）：

- 用户对这个领域/模块的熟悉程度（完全陌生 / 听说过 / 用过但没深入）
- 用户最终想完成什么任务
- 用户已经知道或已经尝试过什么

如果用户在请求里已经说清楚了，跳过提问直接扫描。

### 2. 扫描疆域

**先圈定扫描半径**：按"对本次任务决策的影响"决定扫多深，不追求扫全。超出半径的部分列入报告的「未扫区域」，如实声明——未扫区域本身就是盲区信息的一部分。

**代码库任务**，至少覆盖这些扫描面：

- 相关模块的入口、数据流、已有约定、依赖关系
- **git 历史**：这块代码最近谁在改、改动频率如何（高频改动区 = 认知易过期的高风险区）
- **`TODO` / `FIXME` / `HACK` 标记**：前人留下的显式盲区声明
- **既有 utils / 公共方法 / 相似实现**：项目里已经解决过的问题，新人最容易在这里重复造轮子
- **相邻测试的断言**：测试是「好的标准」的最硬证据；无测试覆盖本身也是一个发现
- 历史坑：git log 中的 fix / revert / hotfix 记录

**领域知识任务**（如调色、视频剪辑、某个协议）：结合自身知识和必要的网络搜索，梳理该领域的基本概念和质量标准。

### 3. 输出盲区报告

按四个维度组织发现，重点放在后两类：

1. **你已经知道的**（简单确认，一两句带过）
2. **你知道自己不知道的**（用户已意识到的问题，给出答案或指路）
3. **你以为显而易见但需要说破的**（代码库里的隐含约定、领域里的默认做法）
4. **你压根没考虑过的**（未知的未知——坑、边界情况、历史包袱、「好」的标准、被忽略的替代方案）

每一条都要解释「为什么这会影响你的决策」，而不是罗列名词。

**每条发现必须标注可信度来源**：

- 代码库结论：给出 `file:line`、git 记录或测试断言作为锚点
- 领域知识结论：区分「通用领域共识」和「基于当前上下文的推断」
- 无法验证的判断：显式标 `[推测]`，并说明用什么方式可以确认

报告末尾附「**未扫区域**」：声明哪些相关部分本次没有扫、为什么（超出决策影响半径 / 无权限 / 时间盒），让用户知道地图上哪些地方仍是空白。

### 4. 教到能做判断为止

对领域类任务，补一段最小教学：这个领域「好」和「差」的判断标准是什么，常见的质量维度有哪些。目标是让用户看到结果时能认出好坏，而不是成为专家。

### 5. 帮用户重写需求

基于扫描结果，主动给出一版改进后的需求草稿，固定包含四部分：

1. **目标**：这次到底要做成什么
2. **硬约束**：扫描发现的、不可绕过的技术与业务约束
3. **Non-goals**：本次明确不碰什么（防止范围蔓延）
4. **留给用户的决策点**：哪些问题只有用户能拍板（取舍、优先级、产品行为）——这是重写需求最大的价值：把「你必须决定的事」从盲区里捞出来摆到明面，而不是替用户偷偷决定

让用户确认或调整，不要直接当作最终需求开始执行。

## Red Lines

- 严禁把未验证的推测写成事实；每条代码库发现必须有锚点，推测必须带 `[推测]` 标记
- 严禁为了填满四维度报告结构而虚构坑点——如果扫描后发现用户的理解已经够动手了，如实说「没有实质盲区，可以开工」，这是合格的扫描结果而不是失败
- 严禁假装扫全了；扫描半径之外的部分必须列入「未扫区域」
- 严禁替用户做只有用户能做的决策，然后把它藏在需求草稿里
- 这是一个只读的认知任务：**只扫描和解释，不修改任何文件**

## 注意事项

- 报告要按「对用户决策的影响大小」排序，不要按扫描顺序流水账
- 发现的内容较多时，输出为 Markdown 报告文件到 `.__docs` 目录供用户留存，聊天中给摘要

## Output Checklist

发送前检查：

- 每条代码库发现是否都有 `file:line` / git / 测试锚点
- 推测是否都标了 `[推测]` 并给出验证路径
- 是否声明了未扫区域
- 需求草稿是否包含目标、硬约束、non-goals、用户决策点四部分
- 是否把「没有实质盲区」也当作一种诚实的可能结论
- 报告是否按决策影响排序

## Failure Modes To Block

遇到这些倾向，要主动拦住：

- "报告显得太薄了，再挖几个坑凑一下"
- "这个约定应该是这样的，直接写进隐含约定里"（没验证）
- "历史上大概踩过这种坑"（没有 git 证据）
- "需求我帮他全写好了，直接照着做就行"（吞掉了用户决策点）
- "相关的 300 个文件我都扫一遍"（无半径控制的流水账）
