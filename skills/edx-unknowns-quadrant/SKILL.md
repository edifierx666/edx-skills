# Unknowns Quadrant (未知四象限)

## ⚠️ 核心纪律：绝对禁止虚构

**这个 skill 的生命线是真实性。每个盲区必须基于真实调查，绝对不能凭空编造。**

### 证据状态标签

为避免把事实、推断和建议混在一起，统一使用以下标签：

- **confirmed / 已确认**：有直接代码、契约、运行或历史证据支持。
- **inferred / 推断**：由多个证据推导出的判断，必须写明依据，不得伪装成事实。
- **unknown / 未确认**：当前调查无法确认，明确列出缺口或未覆盖范围。
- **proposed / 建议**：面向用户目标的方案、优先级或路线，不等同于调查事实。

1. **文件路径必须真实存在**：先搜索、打开、确认内容，再引用；禁止凭印象写路径。
2. **每个「实际上」必须有代码证据**：写清文件、行号、函数名，如 `src/middleware/auth.ts L23-45`。
3. **每个「历史上」必须有 Git 或 issue 佐证**：给出 commit hash、日期或 issue 编号。
4. **无法确认时诚实标注「未能确认」**：如实写「调查后未发现 [某类盲区]，但以下领域未覆盖：[列出]」，禁止为了让某个象限「有东西可说」而编造。
5. **本 skill 所有示例中的路径与内容均为虚构，仅作格式参考**：禁止复制示例路径，必须填入真实调查结果。

**核心承诺：宁可输出「调查后未发现盲区」，也不要编造虚假信息。**

虚构 vs 真实调查的完整对照见 `references/anti-patterns.md` 第一条。

---

**地图不是疆域。**

- **地图**：用户对任务的描述（prompt、需求、理解）
- **疆域**：真实的代码库、约束条件、技术实现、业务规则

二者之间的差距就是「未知」。未知越多，Agent 基于猜测做决策的风险越大。你的任务是：

1. **绘制四象限未知地图**：将用户相对于当前任务的未知，按「是否意识到」和「是否掌握」两个维度分类。
2. **证据驱动**：每个盲区基于真实代码库、文档、技术栈、业务场景的调查结果。
3. **默认先呈现地图**：事实、推断、未知和建议分开；是否追加建议由用户请求决定。

## 工作流程

### 第一步：理解任务上下文与复杂度评估

从用户请求中提取：**任务目标**（想做什么）、**任务复杂度**（涉及多少模块/技术栈/业务约束）、**当前阶段**（开始前 / 进行中 / 复盘）。

**默认假设用户不熟悉**：即使需求明确，也假设用户对实现路径、技术细节、业务约束不完全了解。

按复杂度决定调查与澄清节奏：

- **简单任务**（单一模块、明确技术栈，如「改一个按钮文案」）→ 直接开始调查。
- **中等复杂**（2-3 个模块、常见技术栈，如「添加一个表单字段」）→ 先进行低风险、只读调查；仅当缺少的信息会改变实现方案、权限边界、数据契约或不可逆操作时，再问 1-2 个关键问题。
- **高度复杂**（跨多模块、不熟悉技术栈、复杂业务，如「重构认证系统」）→ 先建立调查结果和候选方案；只有无法安全继续或必须由用户做取舍时，才问不超过 3 个关键问题。

提问不是默认前置门槛：用户已经提供足够上下文时，不重复询问；低风险、可逆、只读的调查不得因等待澄清而停止。提问原则：优先问「答案会改变架构设计、权限/合规边界、数据契约或不可逆行为」的问题。

- 功能：期望的交互流程？有没有类似功能可参考？要支持哪些边界情况？
- 技术：对该技术栈的熟悉程度？有没有选型偏好？性能/兼容性要求？
- 业务：涉及哪些角色/权限？有没有合规要求？上下游系统有哪些？

### 第二步：调查疆域 (必做)

**不能凭空推测。** 按需覆盖以下五类调查面，实际执行了哪些要如实记入「调查方法总结」：

1. **代码库**：相关模块/组件/API/工具函数、现有实现模式与命名约定、依赖版本与构建链、TODO/FIXME、Git 历史回溯（近 3-6 个月相关变更）、git blame 了解决策背景
2. **文档与契约**：README/架构文档/Wiki、类型定义与 schema（TS/GraphQL/Proto/OpenAPI）、测试用例与 Mock、错误/日志/监控规范、CI/CD 配置
3. **技术栈与生态**：框架版本特性与废弃警告、依赖兼容性、行业规范（无障碍/安全/性能/SEO）、浏览器/平台兼容矩阵、环境变量与多环境差异
4. **业务场景**：边界条件（空数据/极值/并发/弱网）、角色与权限、跨平台（移动端/SSR）、上下游依赖、国际化、数据持久化与降级
5. **运行时与可观测性**：错误上报、日志、性能监控、灰度与 Feature Flag、限流

排查 IV 象限时，对照 `references/common-blindspots.md` 中的高频遗漏清单逐类核对（清单条目仍需真实证据才可写入输出）。

### 第三步：按象限分类

默认使用四象限组织信息，但四象限不是唯一允许的呈现方式。用户明确指定排序、优先级、严重度或其他维度时，优先满足用户要求；如同时使用四象限与优先级，明确区分“认知/信息结构”和“实际影响/处理紧迫度”。

- **I. 已知的已知**：不分组，逐个需求点展开
- **II. 已知的未知**：可按**阻塞程度**分组 → 核心疑问（不解决无法推进）/ 待确认细节（影响实现路径）/ 可选探索（可后续优化）
- **III. 未知的已知**：可按**认知距离**分组 → 与假设冲突 / 可直接利用 / 团队约定
- **IV. 未知的未知**：可按**认知距离**分组 → 与假设冲突 / 未考虑场景 / 隐藏风险

**认知距离**指盲区与用户当前认知的差距：与假设冲突（用户以为是 A，实际是 B，最需关注，放最前）＞ 未考虑过 ＞ 可以利用。这样分组符合认知心理——人对「与假设冲突」的信息最敏感；目标是补全认知，不是列 bug 修复清单。

## 关键原则

### 1. 证据驱动，拒绝臆测

- ✅ 「`src/utils/request.ts` 中已有全局错误拦截器，会自动重试 5xx 错误」
- ❌ 「一般来说，项目应该会有错误处理机制」

某领域无法调查（权限不足、文档缺失）时，明确标注「未能确认」。

### 2. 分组与排序

默认按四象限组织，II 可按阻塞程度、III/IV 可按认知距离排列。用户要求按影响、优先级或严重度排序时可以追加或替换排序，但必须标明排序依据，避免把阻塞程度误写成严重度。

### 3. 区分「未知」与「未决策」

- **未知**：客观存在但用户不知道的事实（历史 bug、依赖废弃、现有组件）
- **未决策**：需要用户主观判断的选择（UI 交互细节、性能目标、优先级）

「未决策」放入 **II. 已知的未知**，标注「待确认」。

### 4. 默认先呈现地图，按用户请求决定是否给路线

- 用户只要求未知地图时，不追加建议、prompt 或路线，避免替用户做取舍。
- 用户明确要求建议、优先级、处理路线或推荐方案时，可以在地图后追加独立的“建议/路线”章节。
- 建议必须标记为 **proposed / 建议**，并与 **confirmed / 已确认**、**inferred / 推断**、**unknown / 未确认** 的调查结果分开。
- 不得把“建议你在 prompt 中补充 XXX”等路线内容伪装成调查事实。

### 5. 领域不熟时先做领域盲区扫描

用户表达「我对这个领域一无所知」时（如「不知道什么是调色」）：搜索权威文档与最佳实践 → 列出核心概念、术语、工作流程 → 标注常见陷阱与废弃特性 → 补进 **IV. 未知的未知**。

### 6. 术语零基础解释

根据用户背景和当前任务调整术语解释：用户表现出不熟悉、明确要求白话，或术语首次出现且会影响理解时，补一句大白话说明；对熟悉代码的用户不强制逐项翻译。聊天中贴代码片段时的行尾标注遵循 `inline-code-annotation` skill。

## 自检清单

输出前确认：

- [ ] 每条盲区都有真实的**证据来源**（文件路径、文档链接、调查结果），引用的路径全部真实存在
- [ ] 某象限为空时，如实写「调查后未发现，未覆盖领域：[列出]」，**没有**为凑数而编造条目
- [ ] **I** 每个需求点都有「这是什么」「工作原理」「需确认」
- [ ] 默认使用四象限；若用户指定影响、优先级或严重度，明确标注排序依据并按请求呈现
- [ ] **IV** 来自真实调查发现，且已对照 `references/common-blindspots.md` 逐类核对
- [ ] 仅在用户未要求建议时保持地图-only 输出；若提供建议，已标记为 `proposed / 建议` 并与调查事实分开
- [ ] 「调查方法总结」如实记录执行过的步骤，未覆盖区域已标注
- [ ] 术语、函数名、路径首次出现时都有大白话解释

## 反模式

六种典型失败输出（虚构盲区 / 已知的已知一笔带过 / 空想未知 / 给 prompt 建议 / 未按认知距离分组 / 覆盖不足硬编）的完整对照见 `references/anti-patterns.md`。

## 何时不适用

- 用户已给出详细技术方案，只让你实现 → 直接实现，无需扫盲区
- 用户问「怎么做 X」，期待教程或代码示例 → 给教程，不是未知地图
- 任务过于简单（如「写一个 Hello World」）→ 没有有意义的未知
- 用户明确说「不用分析，直接动手」→ 尊重用户意图

## 与其他 Skill 的协作

- **`api-field-contract-guard`**：未知涉及接口字段时，在 **II** 中标注，具体字段确认流程交给该 skill。
- **`understanding-code-logic`**：用户对代码流程不熟时，先用该 skill 建立心智模型，再做四象限扫描；术语解释规则也以它为准。
- **`reachable-flow-audit`**：未知涉及「代码是否真会执行」时，在 **IV** 中标注可达性风险。
