# 验收考试（Acceptance Quiz）

## 核心理念

一个长 session 结束后，agent 完成的东西往往比用户意识到的多得多。光看 diff 只能获得粗浅理解，因为很多行为取决于已有代码路径。这个 skill 的目标是：**先给用户建立完整上下文，再用测验验证理解，用户全部答对才建议合并。**

这不是给代码打分，而是给用户的理解打分。

## 流程

### 1. 收集改动全貌

- 确认本次改动范围：git diff / 最近 commit / 用户指定的文件列表
- 不只看改了什么行，还要追踪改动如何与既有代码路径交互：谁调用它、它触发什么、哪些行为因此改变
- 找出「不看 diff 也感知不到」的隐性影响：默认值变化、时序变化、边界情况处理、被删除的旧行为

### 2. 生成理解报告

产出一份 HTML 报告（用户明确要求时可用 Markdown），包含：

1. **改动的动机与上下文**：为什么做这次改动，解决什么问题
2. **设计直觉**：关键决策为什么这么选，放弃了哪些替代方案
3. **做了什么**：按数据流/调用链组织，而不是按文件罗列
4. **行为变化清单**：改动前 vs 改动后，用户可感知的差异
5. **风险与边界**：哪些地方最可能出问题，哪些边界情况被处理或被搁置

### 3. 出测验题

在报告底部出一套测验（5-8 题为宜），要求：

- 题目考「理解」而不是「记忆」：优先出"如果输入 X 会发生什么"、"为什么不能直接 Y"、"改动后 Z 场景的行为是什么"这类题
- 覆盖最重要的决策点和最容易被忽略的隐性影响
- 混合选择题和简答题；选择题的干扰项要来自真实的错误理解
- 不在题目旁直接给答案；答案放在报告末尾折叠区或等用户作答后再核对

### 4. 核对与放行

- 用户提交答案后逐题核对，答错的题要解释错在哪、正确理解是什么
- **全部答对才明确建议合并**；有答错的，针对错的部分补充讲解，允许用户重考
- 核对过程中如果发现用户的疑问暴露了代码本身的问题，如实指出，不要为了通过测验淡化问题

## 注意事项

- 这是一个只读的验收任务：**不修改代码，只生成报告和测验**
- 报告文件输出到 `.__docs` 目录（遵循工作区文档输出规范），聊天中告知路径并给摘要
- 改动很小时（几行的 fix），不要硬凑 8 道题，2-3 题足够，或直接建议用户不需要考试
